## K-1 迁移脚本在任何现存环境上都跑不起来

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，三轮审查验证通过） |
| **发现于** | 2026-09-19，Task 1 的代码质量审查（初版由 spec 审查标为「不可重复执行」，质量审查实测后升级） |
| **位置** | `supermall/mall-server/src/main/resources/db/migration/2026-09-18-refund-unique.sql` |
| **严重性** | 高——这是 Task 1 交付物本身的缺陷，不是潜在风险 |

**现状**：迁移脚本是一条合并的 ALTER（`ADD UNIQUE KEY` + `DROP KEY idx_order_id`）。**实测三种环境状态，两种失败**：

| 环境状态 | 结果 |
|---|---|
| 已迁移的 dev（有 uk、无 idx） | `ERROR 1091 Can't DROP 'idx_order_id'` |
| **prod 形态**（uk 与 idx 都在） | `ERROR 1061 Duplicate key name 'uk_refund_order'`，**且 DROP 子句根本不执行**——idx 存活 |
| 全新建库 | ✅ 唯一能跑通的场景 |

**为什么严重**：本仓库没有 flyway/liquibase，`init.sql` 也不自动执行（`application.yml` 无 `spring.sql.init`），所以**这个文件就是操作流程的唯一持久载体**。prod 上的人会撞 1061，合理地判断「已迁移，无需处理」——而这是错的，用户明确要求删除的冗余索引会永久留存。

**原验证的盲区**：implementer 曾用临时库验证「迁移保真度」，但那个库是从 `66f6785` 的建表语句建的——**恰好是唯一能跑的「全新建库」场景**。那次验证证明的是「DDL 语法正确」，不是「文件能应用」。

**修复方案**（已派工）：改为 `information_schema` 自判断写法，使四种状态都正确——全新（加 uk 删 idx）、prod 形态（只删 idx）、已迁移（无操作）、异常（只加 uk）。注意 MySQL 不支持 `DROP INDEX IF EXISTS`，需用变量 + `PREPARE`/`EXECUTE` 动态执行。

**已修复（2026-09-19，提交 `23eadf7`、`afcfad9`、`0d61fa3`）。** 中间还堵掉了两轮审查发现的同类残留静默失败：按索引类型（`non_unique`）判定、以及按**索引精确形状**判定（`@uk_ok` = 恰好单列且该列是 `order_id`）。第三轮审查独立验证了 10 种状态，并确认复合唯一、错列、DESC、INVISIBLE、**函数索引**（MySQL 8 边界：`column_name` 为 NULL）均无误判。

### K-1 残留语义（后期留意，非缺陷）

1. **`@uk_ok` 的判据是「恰好单列」**。所以将来若**有意**把 `uk_refund_order` 改成复合索引（如 `(order_id, status)` 求更精细的唯一性），**本迁移脚本会把它重建回单列**。当前 spec 要求「一单一退」，这是正确行为；但设计变更时脚本会跟设计打架——届时须同步更新该脚本与索引清单。
2. **`-D` 的防护是「报错」而非「不可能出错」**：`-D mall_wrong_db` 仍会作用到那个库。比脚本内写死 `USE mall;` 好（目标库出现在命令历史与 CI 日志里，可审计），但根本上仍依赖操作者传对库名。

## K-4 退款存在两条写路径

| | |
|---|---|
| **状态** | **不必改代码**（2026-09-19 按「取舍准绳」判定）；但**该补一句说明**，见下 |
| **发现于** | 2026-09-19，执行前的计划审查；代码质量审查补充了具体后果（见 K-6） |
| **位置** | `OrderController.java:62`（`POST /{id}/refund`）与计划 A 新增的 `POST /{id}/refund/execute` |
| **处理时机** | 计划 A 完成后、接 MCP 之前 |

**现状**：既有端点走 `orderService.requestRefund`，插入一条 `PENDING`；新端点走全新的幂等执行路径。计划声明「不改动任何现有接口的行为，全部是新增」，所以两条并存。

**影响**：调用旧端点后，新端点的资格查询会返回「已有退款记录」。自洽（一单一退，由唯一索引兜底），但用户有两条入口、行为不同（旧的只落 PENDING 不推进订单状态，新的推进到 `REFUNDED`）。

**注**：`RefundDTO` 本来就只有 `reason`、没有 `amount`，**不存在**「旧端点可指定金额」的安全漏洞。

**判定（2026-09-19，按「取舍准绳」）**：**不改代码**。两条写路径并存符合计划的「纯增量」原则——旧端点是既有能力，动它没有收益。真正承载架构叙事的是**新路径的幂等**，那由唯一索引 + 行锁保证，已经立住了。

**但该补一句话说明**：在 README 或计划里写明「为什么两个退款端点并存、agent 走哪条」。这不是为了合规，是为了**别在演示时被问住**——「你为什么有两个退款接口」是个很自然的提问，答不上来会把「纯增量」这个有意的设计选择显得像疏漏。

**准备好这个追问（2026-09-19 由 Task 3 的质量审查提出）**：

> **「同一个仓库里，优惠券撞唯一键返回既有记录（`CouponServiceImpl.java:94-101`），退款撞唯一键却报错，为什么不一样？」**

答案：**两者服务不同的调用方与语义**。

- 旧退款端点是**「申请」**语义——**重复申请本身就是错误**，应当告诉调用方「你已经申请过了」。
- 优惠券领用是**「幂等获取」**语义——重复领取返回同一张券是**期望行为**。
- 真正的幂等退款在新端点 `refund/execute`（Task 5），它**确实**返回既有结果而不报错。

这个对比反而是个**加分点**：它说明「幂等」不是一刀切的，而是**按业务语义分别设计**的。

## K-8 被驳回的退款会永久阻塞该订单的后续申请

| | |
|---|---|
| **状态** | **不必改代码**（2026-09-19 按「取舍准绳」判定）；**写进计划的「已知简化」清单**，见下 |
| **发现于** | 2026-09-19，Task 1 的代码质量审查（计划层问题，非实现缺陷） |
| **位置** | 计划 A 的「已知简化」清单（第 1295-1301 行）应补入 |
| **处理时机** | 商家审批流落地之前 |

**现状**：退款行**永不删除**，且没有逻辑删除列。所以一条最终为 `REJECTED` 的退款会**永久**阻塞该订单的后续退款——「先驳回、再重新申请」变得不可能。

**当前是否触发**：**否，是潜在问题**。现在没有任何代码写 `REJECTED`；`docs/implementation-plan.md:411-412` 描述的 `/api/merchant/refunds/{id}/approve|reject` 端点在代码里**不存在**（grep `module/merchant` 无退款相关代码）。

**但**：`CLAUDE.md:178` 把退款生命周期描述为 PENDING/APPROVED/REJECTED/COMPLETED，说明商家审批流是**已规划**的。届时会触发。

**需要一并决定**：Task 4 的 `refundExists` 对一条 `REJECTED` 行应当如何解释——按当前逻辑，它会让订单永久不可退。

**建议**：写进计划 A 的「已知简化」清单（那里已有三条同类条目），并明确 `refundExists` 的语义。

**关联陷阱（2026-09-19 追加核实）**：supermall 的 `application.yml` 配了 **MyBatis-Plus 全局逻辑删除**——

```yaml
mybatis-plus.global-config.db-config.logic-delete-field: deleted
logic-delete-value: 1
```

`Refund` PO 当前**没有** `deleted` 字段，所以逻辑删除不生效（这是好事，`refund` 的 `order_id` 唯一索引不会被软删除行污染）。

**但这是个陷阱**：全局配置意味着，**只要有人给 `Refund` PO 加一个名为 `deleted` 的字段**，MP 就会自动接管为逻辑删除——而**软删除的行依然占用 `order_id` 唯一索引**。届时「软删除退款 → 重新申请」看起来可行、实际仍被唯一索引挡住，且没有任何报错提示原因。

排查这一点本身就花了时间：`Refund` 的**表**和 **PO** 都没有 `deleted`，但**全局配置**存在。将来若决定用软删除解决本条，必须先处理唯一索引（例如改为 `UNIQUE KEY (order_id, deleted)` 之类的复合形式或部分索引方案），否则会得到一个静默失效的修复。

**判定（2026-09-19，按「取舍准绳」）**：**不改代码**。本条**当前不触发**——没有任何代码写 `REJECTED`，商家审批流（`/api/merchant/refunds/{id}/approve|reject`）在代码里根本不存在。现在修它等于**为一个不存在的功能做设计**。

**要做的只有一件事**：把本条写进计划 A 的「已知简化」清单（那里已有三条同类条目）。**成本是一行字，收益是显示你知道这条边界在哪**——而这恰恰是这类项目要展示的东西：不是「没想过」，而是「想过、知道边界、有意划在范围外」。

## K-10 迁移脚本的 `USE mall;` 会让临时库测试静默打到真库

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，Task 1 第三轮改为 `-D mall` 并经审查独立验证） |
| **发现于** | 2026-09-19，Task 1 的修复过程中 implementer 自己踩到并上报 |
| **位置** | `supermall/.../db/migration/2026-09-18-refund-unique.sql:53` |
| **处理时机** | 出现第二个迁移脚本时 |

**现状**：脚本硬编码了 `USE mall;`（这是为了让不带 `-D` 执行时不报 `ERROR 1046 No database selected`）。**代价**：任何人在临时库上测试这个脚本时，如果没有改掉这一行，脚本会**静默地作用到真实的 `mall` 库**——不报错、不提示。

implementer 自己就是靠「把测试副本里的 `USE` 那一行替换成临时库名」才完成测试的，并主动上报了这个顾虑。

**影响**：当前只有本机一个环境、一个脚本，风险可控。但若被当作模板复制（计划 B/C 若新增迁移，或将来多人协作），这是一个**会静默改到真库**的陷阱。

**可能的处理方向**：
- 保持现状，靠执行者自觉（脚本头部已注明「要迁移别的库只需改这一行」）
- 改为表名限定 `mall.refund`（同样需要改一处，但错改时更容易发现）
- 库名参数化（MySQL 脚本对参数化支持较差，成本高）

**决定（2026-09-19）**：**去掉 `USE mall;`，改在调用方式里写 `-D mall`。**

方案由代码质量审查者在重审时提出，它**明确承认这是它自己上轮 Minor 建议的错**——它把一个响亮的无害失败（`ERROR 1046`）换成了静默打错库的风险。新方案在四个方面更优：

| | `USE mall;`（旧） | `-D mall`（新） |
|---|---|---|
| 跨环境一致性 | 每个环境要改跟踪的文件——**正是导致 K-1 的漂移模式** | 文件逐字一致，不用改 |
| 目标库可见性 | 藏在脚本里 | 出现在 shell 历史与 CI 日志 |
| 临时库测试 | 必须改文件，忘了就打到真库 | `-D mall_scratch`，无需改文件 |
| 忘加参数 | **静默写生产库** | 无害的 `ERROR 1046` |

**注**：`information_schema` 查询用的是 `DATABASE()`，`-D` 指定的库正是它返回的值，所以判定逻辑不受影响（已要求实现时验证这一点）。

## K-11 计划里的 Maven 命令在本环境跑不通

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，用户选定方案 a，计划已修订） |
| **发现于** | 2026-09-19，Task 2 的 implementer 执行时发现 |
| **位置** | 计划 A 全文的验证命令，如 `mvn test -pl mall-server -Dtest=XXX` |
| **处理时机** | 建议在计划 A 收尾时统一修订计划文档 |

**现状**：`mall-common` / `mall-security` / `mall-infra` **从未 install 到本地 Maven 仓库**（`~/.m2/repository/com/mall/` 下只有 `.lastUpdated` 失败标记）。因此只带 `-pl mall-server` 会直接 `Could not resolve dependencies`，**连编译都到不了**。

**可用的命令**：

```bash
cd /d/sourcecode/supermall && JAVA_HOME=/d/jdks/openjdk-22.0.2 \
  "/d/JetBrains/IntelliJ IDEA 2026.2/plugins/maven-plugin/lib/maven3/bin/mvn.cmd" \
  test -pl mall-server -am -Dtest=XXX -Dsurefire.failIfNoSpecifiedTests=false
```

两个改动的作用：`-am`（also make）让反应堆先构建三个兄弟模块；`-Dsurefire.failIfNoSpecifiedTests=false` 避免兄弟模块因无匹配测试而报错。

**影响**：计划 A 里所有 `-pl mall-server` 的验证命令**照抄会失败**。这不是代码问题，是环境/流程问题，但会让照计划执行的人卡住。Task 8 有全量 `mvn test`，需另行确认是否也需要 `-am`。

**决定（2026-09-19）**：**采用方案 a——计划里所有 `-pl mall-server` 的命令补上 `-am` 与 `-Dsurefire.failIfNoSpecifiedTests=false`，已全部改完（10 处）。**

**为什么不选方案 b（先 `mvn install` 一次）**——它有**静默陷阱**：`install` 把构件写进全局的 `~/.m2`，之后 `-pl` 就从那里取。**只要有人改了 `mall-common` 等模块而忘了重装，测试就会静默地跑在旧代码上**（签名变了会编译失败、响亮；**签名没变而行为变了则完全无声**）。而 Task 3 已经改过 `mall-common` 的 `ResultStatus`，将来还会改。

`-am` **永远从源码构建，不可能解析到陈旧构件**。代价只是每条命令多十几秒的增量重建。

**这与本项目的既有教训同源**：K-1 与 K-2 讲的都是「**靠约定维护的一致性迟早漂移**」。`mvn install` 是又一个「靠人记得」的约定；`-am` 是机制上不可能出错的那一类。**计划里所有命令自带 `-am`，比写一句「记得先 install」更符合这个项目要讲的故事。**

**已在计划里加了一段说明**（「命令约定」小节），解释这两个参数**为什么**必要——否则下一个人看到会以为是多余的。也写明**不要**改成 install 方案及原因。

## K-12 政策枚举的两处语义边界

| | |
|---|---|
| **状态** | **不处理**（用户 2026-09-19 裁定） |
| **发现于** | 2026-09-19，Task 2 的 implementer 主动上报 |
| **位置** | `supermall/.../order/enums/AfterSalesPolicy.java` |
| **处理时机** | 不适用 |

**裁定（2026-09-19）**：**两条都不处理。** 用户理由——**本项目的目的是展现架构与技术栈，不是做生产级系统**（详见文件头的「取舍准绳」）。审查者判定这两条在生产标准下真实存在，但它们既不承载架构叙事，修了也不出彩。

因此下面审查者给出的分析**仅作为记录保留**（它们本身质量很高，将来若真要上生产可直接取用），**不作为待办**。特别地：Task 4 **不**加 `Math.max(0, …)` 守卫，`resolve` 的签名**不**改。

---

**第 1 条：负的 `daysSinceReceipt` 会被静默放行**

`SEVEN_DAY_NO_REASON.appliesTo("RECEIVED", -1)` 返回 `true`（因为 `-1 <= 7`）。

若调用方用 `now - 签收时间` 计算天数，而签收时间戳缺失、写入晚于状态变更、或存在时钟偏移，就可能得到负数并**错误命中 7 天无理由**。计划给的测试未覆盖负值。

Task 4 的 `RefundEligibilityServiceImpl` 里有个 `daysSince()` 辅助方法，它处理了 `from == null`（返回 0），但**没有处理未来的时间戳**。而 `order.created_at` 是 `NOT NULL DEFAULT CURRENT_TIMESTAMP`，所以实际触发需要时钟偏移或手工写入未来时间——**风险低**。

**决定（2026-09-19，代码质量审查判定）**：**低危。守卫放在 Task 4 的调用点，不要放在枚举里。**

两个理由：

1. **实际不可达**：Task 4 用 `Duration.between(order.getCreatedAt(), now).toDays()`，而 `toDays()` **向零截断**——现实中的主机/数据库时钟偏移（秒到小时级）得到的是 **0** 而非负数。要产生负数需要**整整 ≥24 小时**的偏移。真正可利用的窗口是「有人手工写入未来时间戳」，属于数据篡改而非运行时路径。
2. **守在枚举里会产生反效果**：加 `daysSinceReceipt >= 0 &&` 会让负数落到 `QUALITY_ISSUE` 而不是 `SEVEN_DAY_NO_REASON`——**因为一个数据故障而剥夺用户更宽松的政策**。正确做法是 Task 4 的 `daysSince` 里用 `Math.max(0, …)`，这既给出对用户有利的解读，也顺带归一化了不足一天的偏移。

**顺带发现的更大问题**：计划「已知简化 #1」（用 `order.created_at` 近似签收时间）的偏差**方向相反且更大**——订单在 `PAID`/`SHIPPED` 会滞留 1~3 天，导致**合法的第 6 天申请被拒**（过度拒绝）。若要动窗口计算，这一条比负数问题值得优先处理。

**第 2 条：7 天内的质量问题会被归类为「7 天无理由」**

这是计划**刻意锁定**的语义——`resolve_shouldReturnFirstMatchingPolicyInPriorityOrder` 明确断言「签收 2 天时返回 `SEVEN_DAY_NO_REASON`」。但 `resolve(String, long)` 的签名**看不到「用户主张的是质量问题」**，所以第 2 天提出的质量投诉会拿到「7 天无理由」的标题与条款文本。

**为什么这要紧**：两者在下游通常含义不同——**无理由退货一般运费由买家承担，质量问题一般由卖家承担**。这直接影响 Agent 组织给用户的解释，而「解释不得与判定结果矛盾」是阶段 4 的评测项之一。

**决定（2026-09-19，代码质量审查判定）**：**暂不改签名，但要加 javadoc，并绑一个具体触发点。**

**为什么现在不改**：

1. **当前不可观测**——Task 5 是整单退款，系统里**根本没有运费字段、也没有部分退款**。所以「无理由 vs 质量问题」产生**逐字节相同的用户可见结果**。唯一的真实差异（退货邮费谁承担）是系统尚未建模的字段。
2. **它不是 §4.2 的违反**——代码的判定（符合资格、依据政策 X）与政策 X 的文本是一致的；欠明确的是**输入**，不是那个配对。核心不变量完好。
3. **现在改也不便宜**——`resolve` → Task 4 → `RefundEligibilityVO.policyCode` → Task 6 端点 → 计划 B 的 MCP schema → 计划 C 的 Agent（**另一个仓库**）。这条链越长，改动越贵。

**已做（2026-09-19）**：在 `resolve` 的 javadoc 里写明它看不到申诉理由、签收 7 天内的质量投诉同样返回 `SEVEN_DAY_NO_REASON`。**这条很关键**——此前该事实**只存在于另一个仓库的 `known-issues.md`**，Task 4/6/7 的作者根本看不到。

**触发点（写进计划「已知简化」清单）**：**运费或部分退款进入模型的那一刻**。那正是两个政策产生财务差异的事件，且必然要动 Task 5/6——签名改动可以搭车，而不是变成一次跨仓库契约破坏。

**另一条候选路线**：审查者指出，由于 Task 7 按 `name()` 暴露**全部**条款，**Agent 可以自行选择引用哪条**（用户陈述缺陷时引用质量条款）——只要每一条可引用的条款都来自同一个枚举，同源性就保住了。但这条路线成立的前提是**「可引用集合 == `resolve` 能返回的集合」**，而那正是上面 I-1 那个可达性问题要保证的事。**若走这条路线，「无政策适用」路径的文案也必须来自枚举**，否则解释没有锚点（见 K-14）。

## K-13 同源在「时间维度」上会破——Task 7 的投递路径无变更检测

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，用户选定**方案一**；Task 7 未开工，零返工。计划已修订：响应体改为 `{fingerprint, clauses}`） |
| **发现于** | 2026-09-19，Task 2 的代码质量审查 |
| **位置** | 计划 A 的 Task 7（`GET /api/after-sales/policies`）与 spec §4.2 |
| **处理时机** | **写 Task 7 的计划文本之前**——该任务尚未编写，此刻改成本最低 |

**现状**：spec 说「agent 启动时拉取并索引」条款文本。但**没有任何机制告诉 agent 服务端的 `clauseText` 变了**。改动枚举里的一条条款、重新部署 supermall，agent 会**继续引用旧文本**。

**为什么这是真问题**：§4.2 要求一致性必须是**结构性**的，不能靠约定。而「agent 需要时会重新拉取」**正是一种约定**。空间维度上的同源（判定与文本在同一个枚举里）已经做到了，**时间维度上的同源还没有**。

**修复方向**：让 `GET /api/after-sales/policies` 在返回条款的同时返回一个**版本/指纹**（例如对所有常量的 `name()|title|clauseText` 求哈希，或用 `POLICY_VERSION` 常量），agent 刷新时比对。

**最低可行版本**：至少在启动时把指纹打进日志，让漂移**可诊断**。

**为什么用「从枚举派生的哈希」而不是手写版本号**：本仓库**没有任何版本追踪机制**（见 K-2），手写的版本号**自己就会漂移**。从枚举派生出来的指纹是唯一不会自己失效的机制。

### 决定（2026-09-19）：采用方案一，响应体改为 `{fingerprint, clauses}`

**三个候选与选定理由**：

| 方案 | 代价 | 问题 |
|---|---|---|
| **一、包装 VO**（**选定**） | Task 7 自己的测试断言要改 | 无——条款与指纹在**同一次响应**里天然自洽 |
| 二、另开指纹端点 | 纯增量、零破坏 | agent 要两次往返，**两份响应之间有 TOCTOU 窗口** |
| 三、只加启动日志 | 零 | 即 K-13 的「最低可行版本」——漂移**可诊断但不可自动检测**，核心论点未解决 |

**选方案一而不是二**：方案二为了「不动既有形状」而付出一个真实的 TOCTOU 窗口——
**为兼容性牺牲正确性**，而本项目要展示的恰恰是「一致性是结构性的」。

**代价的核实**：计划 B 的 `listPolicyClauses()` 只是把响应体原样 `toString()` 透传给模型
（计划 B 第 865 行），**没有任何测试断言其形状**。所以跨仓库契约实际上**没有消费者**，
改形状的代价只落在 Task 7 自己的两个测试上——选定前已实测确认，不是估计。

**实现细节里两条承载架构主张的设计**：

1. **指纹由「本次实际返回的那批条款」算出**（`PolicyCatalogVO.of(clauses)`），不是另算一份。
   于是「指纹覆盖的内容」与「响应里的内容」是**同一个列表**——**结构性保证，不是约定**。
2. **指纹对顺序敏感**，因为本项目的政策枚举**顺序即优先级**（见 K-16）。
   调换顺序会改变判定结果，因此也必须改变指纹；否则一次「静默改了优先级」的发布，
   agent 侧会认为条款没变而继续用旧顺序解释。

**为什么这不只是生产硬化**：它关闭的是 §4.2「同源」在**时间维度**上的缺口，
而同源约定正是本项目取舍准绳里明确「该修」的架构主张之一。K-13 因此不是伪缺陷。
**但也要承认**：这是该主张延伸到较远处的一条——若条款文本在实际使用中根本不变，
本条的收益会很低。当前判断是「值得修」，代价确实小。

## K-14 「无政策适用」这条路径的文案不是同源的

| | |
|---|---|
| **状态** | **不必修**（2026-09-19 按「取舍准绳」判定，理由见下） |
| **发现于** | 2026-09-19，Task 2 的代码质量审查 |
| **位置** | `AfterSalesPolicy.resolve` 返回 `null` 的场景；Task 4 的 `RefundEligibilityServiceImpl` |

## K-23 测试里 `BigDecimal` 断言的 scale 敏感性

## K-24 Task 4→Task 5 的接缝断裂（**已修复**，但仍值得记）

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，计划已修订；Task 5 未开工，故零返工） |
| **发现于** | 2026-09-19，Task 4 的代码质量审查 |
| **位置** | 计划 A 的 Task 5 `RefundExecutionServiceImpl.execute` |
| **严重性** | **Critical（审查者判定）**——且它不在 Task 4 的 diff 里，而在它**交出去的契约**里 |

**问题**：`check()` 只要有退款行就返回 `eligible=false`；而 `execute()` 第一件事就是 `check()`，`!eligible` 直接 `throw ORDER_NOT_REFUNDABLE`（50002）。**后果是计划里那段幂等分支（注释写着「Agent 重试会走到这里」）在真实组合下永远不可达。**

**为什么计划自己的测试是绿的**：`givenEligible()` 把 `check()` **stub 成了 `eligible=true`**——而现实中只要退款行存在，`check()` 绝不会返回 true。**那个 stub 恰好把会拦住它的组件换掉了**，所以它通过不代表真实组合通过。

**这不是理论**：计划 Task 8 的 Step 5 期望「重复执行返回成功（不报错）」，按原计划会返回 50002，**验收标准当场不通过**。

**第二处（并发）**：计划注释「锁后再查一次退款记录才可靠」**是错的**。`execute()` 是 `@Transactional`，`check()` 里的 `selectById` 已建立本事务的 read view；InnoDB 在 REPEATABLE READ 下不刷新它，而 `selectByIdForUpdate` **只刷新被锁的那一行，不刷新快照**。所以复查可能读到 0 行 → 撞 `uk_refund_order` → 原计划**没有 catch** → `-1 系统异常`，正是 K-6 刚替旧端点修掉的那个坑。

**审查者在 MySQL 8.0.40 上用双会话隔离级别实验实测确认了这个行为**（不是推理）。

**修复（已落进计划）**：

1. 守卫条件改为把「已有退款」认成**重试**而非拒绝：
   ```java
   if (!eligibility.isEligible() && !eligibility.isRefundExists()) { throw ... }
   ```
2. `insert` 外包 `catch (DuplicateKeyException)` → 走幂等返回。**唯一索引是并发裁判，代码只负责把它翻译成业务语义**——与 Task 3 已批准落地的 `OrderServiceImpl` 写法同源。
3. 补 3 个测试：真实形态的顺序重试、`PENDING` 行的文案、并发撞唯一键的翻译。

## K-26 Task 5 的并发兜底分支从未生效（**已修复**）

| | |
|---|---|
| **状态** | **已处理**（2026-09-19。计划修订 `5af759e`；supermall 实现修复 `e070723` + 注释订正 `b43e161`；Task 8 增补并发验证步骤。**质量审查的变异测试确认缺口真被堵上**） |
| **发现于** | 2026-09-19，Task 5 的 implementer 自审时提出疑虑，**主控独立验证后确认并加强** |
| **位置** | 计划 A 的 Task 5 `RefundExecutionServiceImpl.execute` 的 `catch (DuplicateKeyException)` |
| **严重性** | **高——交付物缺陷**（幂等属取舍准绳里明确「该修」的架构主张）。但**钱始终是安全的**，坏的是响应形态 |

**现状**：catch 分支用**普通 `selectOne`** 复查并发赢家，并注释「**理论上不可达**：能撞上 `uk_refund_order` 就说明那行存在」。

**为什么这句说反了——不是「偶尔读不到」，是担保性失败**：

1. `execute()` 标注 `@Transactional`，而 `check()` 开头的 `orderMapper.selectById`（`RefundEligibilityServiceImpl.java:33`）是**普通 SELECT**，**已经在本事务里建立了 read view**
2. `application.yml` **未配置隔离级别**，MySQL 全局与会话实测均为 **`REPEATABLE-READ`**
3. REPEATABLE READ 下普通 SELECT **只复用**该 read view，**不会刷新**

于是 catch 的两个入口条件与复查的可见性**恰好互补，互为充要**：

| 赢家提交时刻 | 结果 |
|---|---|
| **早于**本事务 read view | 上方 `existing` 复查就看得见 → 提前正常返回，**进不了 catch** |
| **晚于**本事务 read view | 进 catch → catch 里也是普通 SELECT，复用同一旧 view → **必定读不到** |

**「进入 catch」与「复查能成功」互斥**，所以 `winner == null` → `throw e` 是**唯一可达的出口**。这条分支对它声称要处理的场景**从未生效过**，并发重试会稳定漏成 `-1 系统异常`——**正是它存在所要避免的结果**。

**为什么此前没被发现，且单测永远抓不到**：catch 里那次读被 Mockito stub 掉，stub 什么就返回什么，**行为断言必然全绿**。计划初稿的测试注释写「catch 里的第二次查询读得到（**新语句，新快照**）」——那是 **READ COMMITTED 的语义**，与本项目实际配置不符。**测试把错误假设写进了注释，于是它自己也失去了质疑能力。**

**修复**：catch 改用**锁定读**（`RefundMapper.selectByOrderIdForUpdate`，`SELECT ... FOR UPDATE` 读最新已提交版本，不受快照约束），写法与既有的 `OrderMapper.selectByIdForUpdate` 同构。**不采用**改隔离级别——那会动摇本方法其余对 REPEATABLE READ 的推理。测试补一条**结构性断言**钉住它。

**为什么不会死锁**（值得记，因为「加锁」通常令人紧张）：两个事务都先 `selectByIdForUpdate` 锁**订单行**，所以同一订单的并发请求在订单行上**串行化**——进入 catch 时赢家早已提交并释放全部锁，那次锁定读是无争用的记录锁。

### K-26 的两条教训

1. **`@Transactional` 方法内「先普通读、后复查」的结构有一个隐形前提**：复查要么是**锁定读**，要么能容忍读到过期快照。本项目里这个前提被违反了，而注释反而把它写成了「理论上不可达」。
2. **单测 stub 掉的那一层，正是 bug 的藏身处**。这条缺陷单测 8/8 全绿、全量 179/179 全绿，**只有真实 MySQL 上的并发调用才现形**——已作为 Task 8 的独立步骤，因为「声称必须可演示」。

## K-27 两处测试脚手架陷阱（Task 5 实测踩到，后续任务可能复现）

| | |
|---|---|
| **状态** | **已处理**（Task 5 已按此写通）；记录供 Task 6/7 与计划 B/C 参考 |
| **发现于** | 2026-09-19，Task 5 的 implementer 实测 |
| **位置** | `RefundExecutionServiceImplTest` |
| **严重性** | 低——纯粹的脚手架问题，不影响任何断言语义 |

**1. MyBatis-Plus 3.5.10 的重载解析歧义。** `BaseMapper` 同时有 `insert(T)` / `insert(Collection<T>)`、`updateById(T)` / `updateById(Collection<T>)`，**无参 `any()` 无法定型**，编译报歧义（实测 4 处）。改用 `any(Refund.class)` / `any(Order.class)`。

> **但理由不是「两者等价」**（2026-09-19 订正，原文写的「`any(Class)` 与 `any()` 一样匹配含 `null` 的任意值」**是错的**）。
> 审查者以 `javap` 实证 Mockito 5.20.0 字节码：无参 `any()` 是 `Any.ANY`，**匹配含 `null` 的任意值**；
> `any(Class)` 走 `InstanceOf`，其 `matches` 对 `null` 直接 `ifnull → false`——**`any(Class)` 更严格**。
>
> 本次结论「断言语义未变」仍然成立，但成立的真正理由是：那 3 处都在 `verify(..., never())` 路径上，
> 而那些路径根本不会调用 `insert`/`updateById`，**不依赖 null 匹配**。
> 若换到依赖 null 匹配的位置，这个替换会**静默改变语义**。

**2. `SnowflakeIdUtil` 在纯单测里不可用。** 它现在必须显式注入 workerId/datacenterId，没有 Spring 容器时调用 `nextId()` 抛 `IllegalStateException`（实测 4 个用例 error）。按本仓库既有约定（`OrderServiceImplTest.java:81`）在 `@BeforeEach` 加 `mockStatic(SnowflakeIdUtil.class)`、`@AfterEach` close。

## K-29 同一句契约文本的每份副本，都是一次「丢掉限定词」的机会

| | |
|---|---|
| **状态** | **记录，并已据此定了一条编辑准则**（2026-09-19） |
| **发现于** | 2026-09-19，Task 5 质量审查 + Task 6 implementer 自审 + 质量审查复核，**四次独立复现** |
| **位置** | `RefundEligibilityVO` 返回契约的各处表述 |
| **严重性** | 中——不是行为缺陷，但**每次都产出一句与事实相反的话**，且都在下游会照抄的位置 |

**现象**：同一件事实——「`eligible=false` / `refundExists=true` 表示此前已有退款记录」——
在三处被分别表述，**三处都丢了同一个限定词**（「既有行可能是 PENDING，此时钱没退」）：

| # | 位置 | 错误表述 | 谁发现 |
|---|---|---|---|
| 1 | `RefundExecutionService` javadoc | 「调用方据此判断『**已经退过了**』」 | 审查者复审自己的稿子时 |
| 2 | 计划 Task 6 的契约表格 | 「`false` 意味着『此前**已退过**、本次未重复执行』」 | 主控自查（写完第 3 条的下一轮） |
| 3 | `OrderController.refundEligibility` javadoc | 「它是那条既有记录的**已退**金额」 | Task 6 implementer 自审 |
| 4 | 计划 Task 6 的契约表格**隔壁一格** | 同上一句（第 3 条修好时它就在旁边，**未被一并看见**） | 质量审查复核 |

**它的形状不是「某句话写错了」，而是**：一句准确的话在被**缩短**成副本时，
**让它准确的那个限定词最容易掉**——而副本往往比原话更接近下游（第 3 处才是经 MCP 到 Agent 的那份）。
四次都不是粗心：每一份单独看都通顺，只有跟事实对照才露馅。

**第 4 次尤其说明问题**：它就在第 3 次的**隔壁一格**——我修第 3 处时，同一张表里紧挨着的那格写着同一句话，**我没看见**。
修一处不等于清一处；**要按「这句话在哪些地方出现过」去搜，而不是按「哪里被指出有错」去改**。

**为什么值得单独记**：本项目「注释不得声称与事实相反」已因同类问题修过 K-3、K-24、K-26、K-28 四次，
本条是它的**第 5、6、7 次**，且集中在一句话上。说明这不是偶发，是**复述结构本身**在制造它。

### 据此定的编辑准则（后续任务请遵守）

1. **同一句契约文本，不要主动增加副本。** Task 6 期间 implementer 曾建议给
   `RefundEligibilityService.check` 也补一份完整 javadoc——**明确拒绝**：那会是第四份副本。
   它的接口 javadoc 保持现状（「只读：判断订单的售后资格与可退金额，无任何副作用」），准确但不复述契约。
2. **复述时必须连同限定词一起搬。** 缩短可以，但**不许**把「可能是 PENDING、钱没退」这个前提留在原地。
3. **改动契约文本时，把所有副本一起改。** 只改其中一处，比不改更糟——它会变成两份互相矛盾的契约。
4. **凡声称「已退 / 已完成 / 已成功」之处，必须问一句：PENDING 时这句话还成立吗？**
   这是四次事故的共同触发点。
5. **权威文本与事实冲突时，以事实为准并回报——不要为了执行指令而制造一条假的记录。**（2026-09-19 补）
   本任务里发生过两次，两次都由下游拦下：
   - 派工给了一段 javadoc，要求「照抄」。执行者落笔前**先去读 `RefundEligibilityServiceImpl` 核实**，
     发现该段漏掉了第三个象限——**没有照抄**，而是先报告事实。它若照抄，缺陷就直接进交付物。
   - 另一次，主控基于**错误前提**指定了一条提交信息（要求重做一次已经做过的改动）。
     执行者核实后发现那会是一个**空提交**，拒绝执行并说明「会让历史里出现一条看似改了东西、
     实则无变更的记录」。

   **这条与上面同源**：它们都是「有一份被当作权威的文本，而它与事实不符」。
   区别只在于那份文本是注释、是计划、还是**一条指令**。**下一条准则对三者一视同仁。**

6. **给下游的指令本身也可能是错的**，而下游没有义务替它圆场。
   执行者的正确动作是：**核实 → 说出事实 → 把选择权交回**，而不是「先照做，有问题再说」。
   对本项目尤其重要——**这个项目的交付物是文档与注释本身**，
   照抄一条错的权威文本，产出的就是一条与事实相反的注释，正是硬规矩禁止的东西。

7. **一致性判据的作用域是「我正在撰写或审阅的文本」∩「本次任务范围」，不是一条可回扫全仓的审计规则。**
   （2026-09-19 补，来自一次实际裁决）
   判据：**与自己所在段落不一致 且 属于本次改动范围 = 改；否则不改。**

   **两个实际案例**：
   - **改**（在同范围内）：`OrderController.java:95` 的 `**不会**` → `<b>不会</b>`。
     该段其余强调全用 `<b>`，它是唯一一个，**看起来像笔误**。
   - **不改**（在范围外）：`MerchantSecurityConfig.java:18` 的 `**第一个匹配到的链**` 与同 `<p>` 段里的
     `<b>` 共存，按「段落」判据**符合改**——但它在**另一个模块**、属既有代码。
     改它会（1）**污染本次 diff**，让提交范围与任务范围脱钩；（2）**开了口子就是全仓重构**
     ——全仓同类写法共 **22 处**（javadoc 13 + `//` 注释 8），今天为一个词改 1 处，明天没理由不改另外 20 处。

   **「既有风格」的硬核实方式**（比判据本身更可靠）：**看该写法在全仓同类构造里有没有先例**。
   例：全仓 `//` 行注释里 `<b>` 出现 **0 次**，故 `//` 里的 `**` 在各自构造内自洽，不该改。

   > **本条差点被漏记**：裁决后我只说了「不改，**也不记录**」，
   > 而 K-21 的体例恰恰是「**记录，不修**」——**不改不等于不记**。是执行者在事后核验隐患清单时指出来的。

8. **「别人说记了」不等于「记了」——记录也要被核验。**（2026-09-19 补）
   团队模式下，落笔隐患清单的是主控，执行者只回报发现。**执行者应当事后 grep 核验自己的发现是否真的进档**，
   而不是相信一句「这条我会记进清单」。本条的三个漏记项正是这么发现的。
   派发同一段文本的修正版之前，先确认前一版**尚未被采用**；否则执行者按旧版落地，
   而旧版同样是「你要求照抄的定稿」，它无从判断作废。
   本条的教训与上面同源——**多一个副本，就多一次有人拿到错那份的机会**，
   只不过这里的「副本」是同一文本的两个时间版本。

> **没有采用的结构性方案**：让端点 javadoc 只写指针、不写内容（消除副本）。
> 未采用的理由是端点 javadoc 是 HTTP 契约面，消费者需要自包含；而当前风险
> 已由审查环节逐次拦下。**这是一个可推翻的取舍。**
>
> **触发条件的诚实交代**：本条目初稿写的推翻条件是「若将来再复现第 4 次」。**第四次确实出现了**，
> 但需要分辨——第 3、4 次是审查者在**同一轮快照**里一起发现的，**都发生在准则写成之前**，
> 所以准则尚未被一次「未来的编辑」检验过。同时也要承认：**准则写完后，我在同一轮的修复里
> 又犯了两次**（把执行接口的取值来源描述错、漏掉第三个象限），两次都由审查者指出。
>
> **当前决定：暂不推翻，但把触发条件重述清楚**——判据不是「累计第几次」，而是
> 「**准则写成之后，是否还有副本在无人指出时自行漂移**」。上面那两次属于「我写新文本时写错」
> （审查拦住了），不属于「副本静默漂移」；后者尚未在准则生效后发生过。若它发生，

## K-30 「超期」走不到那个象限——把资格说窄比说宽更危险

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，spec 审查发现；计划与代码同步订正） |
| **发现于** | 2026-09-19，Task 6 的 spec 审查 |
| **位置** | `OrderController.refundEligibility` javadoc 第三象限的括注 |
| **严重性** | **中高**——不是行为缺陷，但会把 Agent 引向**错误地拒绝一个真正可退的订单** |

**现状**：第三象限（`eligible=false && refundExists=false`）的括注写的是「政策不适用／**超期**」。

**「超期」不可能导致这一支。** `AfterSalesPolicy` 里：

| 政策 | `appliesTo` |
|---|---|
| `SEVEN_DAY_NO_REASON` | `RECEIVED` **且** ≤7 天 |
| `SHIPPED_NOT_RECEIVED` | `SHIPPED` 或 `DELIVERED` |
| **`QUALITY_ISSUE`** | **`RECEIVED`，不受期限限制**（兜底项） |

`QUALITY_ISSUE` 对所有 `RECEIVED` 订单生效，所以**签收 30 天的 `RECEIVED` 订单仍是 `eligible=true`、`policyCode=QUALITY_ISSUE`**。
`resolve()==null` 的**充要条件**是 `orderStatus ∉ {RECEIVED, SHIPPED, DELIVERED}`——实际活例子是 `PENDING`（下单未支付）与 `PAID`（已支付未发货）。

### 这条要记的是**风险方向**，不是措辞

说宽（把不可退说成可退）的后果是 Agent 去尝试一个会失败的操作——**有系统兜底**（状态机、唯一索引、服务端算金额）。
说窄（把可退说成不可退）的后果是**用户被错误拒绝**，而没有任何机制会发现。

**本项目的三道防线全部只防「越权/违规执行」，没有一道防「错误拒绝」。** 所以「把资格说窄」这类错误在本项目里是**不对称地危险**的
——这也是为什么它值得当场改，而不是「记录待判断」。

### 一条关于这个政策引擎的、值得记住的性质

> **天数轴只决定「命中哪条政策」，从不决定「有没有政策」。**

`RECEIVED` + 超 7 天让 `SEVEN_DAY_NO_REASON` 返回 false，但 `QUALITY_ISSUE` **紧接着就接住了**，
于是只是换了个政策码，`resolve` 仍非 null。**任何时候都不要用天数去推断「能不能退」。**

**因此订正后的措辞不硬编码状态清单**（「订单状态不符合任何售后政策」）：
那个等价关系只对**当前枚举内容**成立，且没有测试守着——
`AfterSalesPolicyTest#everyPolicyIsReachableThroughResolve` 守的是**反方向**（防常量被遮蔽），不是防状态无覆盖。
将来新增政策或出现脏状态值，硬编码的清单就会漂。

### 来源

这句「超期」是**上一轮质量审查者建议的措辞，主控照抄未核**。这是 K-29 那个模式的又一例，
但它同时说明了 K-29 规则 5 为什么不够：**建议本身也可能是错的，而「照抄」这个动作不会区分**。

## K-31 `@Valid` 校验失败在全仓范围内返回 `-1 系统异常`（**局部已收口，仓库级未修**）

| | |
|---|---|
| **状态** | **部分处理**（2026-09-19，用户裁定**只在局部收口**；仓库级缺口**有意保留**，见下。实现 `e9adfa5`） |
| **发现于** | 2026-09-19，Task 6 的代码质量审查 |
| **位置** | `GlobalExceptionHandler.java`（缺 handler）；影响全仓 14 个用 `@Valid` 的文件 |
| **严重性** | 中——**本项目已修过两次的同型问题**（405 那次、K-6 修 `DuplicateKeyException` 那次） |

**现状**：`GlobalExceptionHandler` 只有四个 handler——`NullPointerException` / `BusinessException` /
`HttpRequestMethodNotSupportedException` / 兜底 `Exception`。**没有 `MethodArgumentNotValidException`**，
于是任何 `@Valid` 校验失败都落进兜底分支，返回 `{"code":-1,"message":"系统异常"}`。

**为什么对 Agent 特别危险**：`refund/execute` 的 `reason` 是 `@NotBlank @Size(max=512)`，
而 **LLM 很容易把用户的整段抱怨当作 `reason` 递上来**（超 512 字）。此时它收到 `-1`——
在它的判断里等于「售后系统故障」，会诱发重试与升级。Plan B 的客户端把 `code != 0` 抛成异常，
模型据 `code` 决策，所以这个码会**直接影响它的选择**。

**论证与 K-6 完全一致**：K-6 修 `DuplicateKeyException` 就是因为「驱动这个端点的 agent 看到的是系统异常，
会诱发重试与升级」。同一个理由在这里成立。

### 处置：在 `OrderController` 内局部收口（用户 2026-09-19 裁定）

Task 6 在 `OrderController` 内加了一个**局部** `@ExceptionHandler(MethodArgumentNotValidException.class)`
→ `PARAM_ERROR(10000)`。Spring 中控制器内部的 `@ExceptionHandler` 只作用于该控制器且**优先于** `@ControllerAdvice`。

**为什么不做全局**：全局改动会让**提交范围与任务范围脱钩**——这正是同一天
`MerchantSecurityConfig` 那次裁决所立的规则（范围外的问题只报告不改；开了口子就是全仓重构）。

### ⚠️ 实际范围比「售后端点」宽——**措辞已按事实订正两次**

选型时用的标签是「只覆盖售后端点」。**这在 Spring 机制上做不到**：
控制器级 `@ExceptionHandler` 按**控制器**生效，**不按端点**。实际范围是：

| | 端点 | 效果 |
|---|---|---|
| **宽** | `POST /api/orders`（`createOrder`，**建订单，与售后无关**） | 非法参数 `-1` → `10000` |
| **宽** | `POST /api/orders/{id}/refund`（旧退款端点） | 同上 |
| **宽** | `POST /api/orders/{id}/refund/execute`（本任务的） | 同上 |
| **宽** | `GET /api/orders`（`listOrders`，**查询参数**校验） | **同样是 `10000`**，详见下 |
| **窄** | 其余 13 个用 `@Valid` 的文件 | **仍是 `-1`** |

**「保持局部」的原始论据已不成立**：它的理由本是「不动本任务以外的端点」，
但它**已经改变了 `createOrder` 的行为**。三个方案重新列出后，用户仍选**局部修**，
理由换成准确的版本：**影响面限制在一个控制器内（1 个文件 vs 14 个文件）**，而非「零范围外影响」。

### ⚠️⚠️ 第二次订正：`GET /api/orders` 也是「宽」，不是「窄」（2026-09-19 晚，复审发现）

初稿把它列为「窄」，理由是「非请求体的 `@Valid` 抛 `BindException`，
而 handler 声明在**子类** `MethodArgumentNotValidException` 上，收不到父类实例」。

**前提是错的。** 在 spring-web 6.2.5 里，**非请求体的 `@Valid` 失败同样抛 `MethodArgumentNotValidException`**。
源码级证据（我已独立复核）：

```java
// ModelAttributeMethodProcessor.java:157-158
if (binder.getBindingResult().hasErrors() && isBindExceptionRequired(binder, parameter)) {
    throw new MethodArgumentNotValidException(parameter, binder.getBindingResult());
}
// :257-262   isBindExceptionRequired(parameter) → return !hasBindingResult
```

`listOrders(@Valid OrderPageDTO dto)` 后面**没有** `BindingResult` 参数 → `isBindExceptionRequired` 返回 `true`
→ 抛的是 `MethodArgumentNotValidException`。另核：`:134-139` 的 `catch` 是**原样重抛**、从不转成 `BindException`；
spring-web 全文唯一的 `throw new BindException(...)` 在 `WebRequestDataBinder:178` 的 `closeNoCatch()` 里，
**不在绑定路径上**。

**因此「一个 handler 同时覆盖请求体与查询参数两类」**——这一点反过来简化了将来全局修的改法（见下）。

> **这条错误的来源值得记**：implementer 报的是「实测 spring-web 6.2.5 `MethodArgumentNotValidException extends BindException`」——
> **这个前提是真的**，但它据此推出的「所以 `listOrders` 抛的是 `BindException`」**是假的**（真实抛的是子类）。
> 而**主控把结论直接采信、写进了本条与计划**，没有自己看一眼调用点。
> 与 K-29 同族：**「一个真实的前提」也能推出「一个假结论」，而采信结论的人不会察觉**。
> 是复审读 Spring 源码时发现的。

### 残留风险（**不要遗忘这一条**）

**其余 13 个用 `@Valid` 的文件照旧返回 `-1`。** 当前没有 Agent 调用它们，所以不构成问题；
**但只要将来有 Agent 走任何一个 `@Valid` 端点，这个坑就会重新生效。**

**届时的修法**：在 `GlobalExceptionHandler` 加

```java
@ExceptionHandler(MethodArgumentNotValidException.class)
public Result<Void> handleValidation(MethodArgumentNotValidException e) {
    return Result.fail(ResultStatus.PARAM_ERROR);   // 10000，已存在且语义正好
}
```

**只加这一个就够**——它同时覆盖**请求体**与**查询参数**两类校验失败（理由见上面的第二次订正）。

> ⚠️ **不要**照 2026-09-19 初稿那样再加一个 `@ExceptionHandler(BindException.class)`：
> 那条建议建立在「非请求体校验抛 `BindException`」这个**错误前提**上，加了是多余的死代码。

并**删掉 `OrderController` 里那个局部 handler**——否则两处并存，又是一次「同一事实的多个副本」，
且**局部那个会永远赢，全局那个形同虚设**。

> **「为什么局部会赢」的机制要说准**（2026-09-19 订正，原文写「因为更具体而永远赢」是**错的**）：
> `ExceptionHandlerExceptionResolver` **先查 handler 所在类自己的 `@ExceptionHandler` 方法，找不到才遍历 `@ControllerAdvice`**
> ——即赢在**解析顺序**，不是赢在「更具体」。
>
> **差别有实际后果**：若将来局部声明的是**父类**（如 `BindException`）、全局声明的是**子类**
> （如 `MethodArgumentNotValidException`），先被检查的**局部仍然会赢**，与「更具体者胜」的预期**正好相反**。
> 按错误的机制去推理，会得出「只要全局声明得更具体就能盖过局部」这种不成立的结论。

注意它是**行为改动**：会让所有 `@Valid` 端点的非法输入路径从 `-1` 变成 `10000`。
计划开头的「改变既有行为的地方」清单需要**第三次**修订。
