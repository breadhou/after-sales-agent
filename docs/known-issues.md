## K-1 迁移脚本在任何现存环境上都跑不起来

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，三轮审查验证通过） |
| **发现于** | 2026-09-19，Task 1 的代码质量审查（初版由 spec 审查标为「不可重复执行」，质量审查实测后升级） |
| **位置** | `supermall/mall-server/src/main/resources/db/migration/2026-09-18-refund-unique.sql` |
| **严重性** | 高——这是 Task 1 交付物本身的缺陷，不是潜在风险 |

**现状**：迁移脚本是一条合并的 ALTER（`ADD UNIQUE KEY` + `DROP KEY idx_order_id`）。**实测三种环境状态，两种失败**：

| 环境状态 | 结果 |
|---|---|
| 已迁移的 dev（有 uk、无 idx） | `ERROR 1091 Can't DROP 'idx_order_id'` |
| **prod 形态**（uk 与 idx 都在） | `ERROR 1061 Duplicate key name 'uk_refund_order'`，**且 DROP 子句根本不执行**——idx 存活 |
| 全新建库 | ✅ 唯一能跑通的场景 |

**为什么严重**：本仓库没有 flyway/liquibase，`init.sql` 也不自动执行（`application.yml` 无 `spring.sql.init`），所以**这个文件就是操作流程的唯一持久载体**。prod 上的人会撞 1061，合理地判断「已迁移，无需处理」——而这是错的，用户明确要求删除的冗余索引会永久留存。

**原验证的盲区**：implementer 曾用临时库验证「迁移保真度」，但那个库是从 `66f6785` 的建表语句建的——**恰好是唯一能跑的「全新建库」场景**。那次验证证明的是「DDL 语法正确」，不是「文件能应用」。

**修复方案**（已派工）：改为 `information_schema` 自判断写法，使四种状态都正确——全新（加 uk 删 idx）、prod 形态（只删 idx）、已迁移（无操作）、异常（只加 uk）。注意 MySQL 不支持 `DROP INDEX IF EXISTS`，需用变量 + `PREPARE`/`EXECUTE` 动态执行。

**已修复（2026-09-19，提交 `23eadf7`、`afcfad9`、`0d61fa3`）。** 中间还堵掉了两轮审查发现的同类残留静默失败：按索引类型（`non_unique`）判定、以及按**索引精确形状**判定（`@uk_ok` = 恰好单列且该列是 `order_id`）。第三轮审查独立验证了 10 种状态，并确认复合唯一、错列、DESC、INVISIBLE、**函数索引**（MySQL 8 边界：`column_name` 为 NULL）均无误判。

### K-1 残留语义（后期留意，非缺陷）

1. **`@uk_ok` 的判据是「恰好单列」**。所以将来若**有意**把 `uk_refund_order` 改成复合索引（如 `(order_id, status)` 求更精细的唯一性），**本迁移脚本会把它重建回单列**。当前 spec 要求「一单一退」，这是正确行为；但设计变更时脚本会跟设计打架——届时须同步更新该脚本与索引清单。
2. **`-D` 的防护是「报错」而非「不可能出错」**：`-D mall_wrong_db` 仍会作用到那个库。比脚本内写死 `USE mall;` 好（目标库出现在命令历史与 CI 日志里，可审计），但根本上仍依赖操作者传对库名。

## K-4 退款存在两条写路径

| | |
|---|---|
| **状态** | **不必改代码**（2026-09-19 按「取舍准绳」判定）；但**该补一句说明**，见下 |
| **发现于** | 2026-09-19，执行前的计划审查；代码质量审查补充了具体后果（见 K-6） |
| **位置** | `OrderController.java:62`（`POST /{id}/refund`）与计划 A 新增的 `POST /{id}/refund/execute` |
| **处理时机** | 计划 A 完成后、接 MCP 之前 |

**现状**：既有端点走 `orderService.requestRefund`，插入一条 `PENDING`；新端点走全新的幂等执行路径。计划声明「不改动任何现有接口的行为，全部是新增」，所以两条并存。

**影响**：调用旧端点后，新端点的资格查询会返回「已有退款记录」。自洽（一单一退，由唯一索引兜底），但用户有两条入口、行为不同（旧的只落 PENDING 不推进订单状态，新的推进到 `REFUNDED`）。

**注**：`RefundDTO` 本来就只有 `reason`、没有 `amount`，**不存在**「旧端点可指定金额」的安全漏洞。

**判定（2026-09-19，按「取舍准绳」）**：**不改代码**。两条写路径并存符合计划的「纯增量」原则——旧端点是既有能力，动它没有收益。真正承载架构叙事的是**新路径的幂等**，那由唯一索引 + 行锁保证，已经立住了。

**但该补一句话说明**：在 README 或计划里写明「为什么两个退款端点并存、agent 走哪条」。这不是为了合规，是为了**别在演示时被问住**——「你为什么有两个退款接口」是个很自然的提问，答不上来会把「纯增量」这个有意的设计选择显得像疏漏。

## K-6 旧退款端点被拒时会返回「系统异常」

| | |
|---|---|
| **状态** | **待修**（用户 2026-09-19 决定处理）——折进 Task 3 |
| **发现于** | 2026-09-19，Task 1 的代码质量审查 |
| **位置** | `OrderServiceImpl.java:264-288`（插入点在 286）；`GlobalExceptionHandler.java:39-43` |
| **处理时机** | 建议折进 Task 3（`REFUND_ALREADY_EXISTS(50003)` 正好在那里引入） |

**现状**：`requestRefund` 没有重复校验。唯一索引落地后，**第二次** `POST /api/orders/{id}/refund` 会抛 `DuplicateKeyException` → 通用处理器 → `Result.fail(ResultStatus.EXCEPTION)`（`-1 系统异常`）+ 一条 `unknown_failure` ERROR 日志。

**影响**：
- 失败方向是安全的（fail-closed，不会写入重复退款）
- 但**驱动这个端点的 agent 看到的是「系统异常」，与真实故障无法区分**，会诱发重试与升级
- 计划第 34 行「不改动任何现有接口的行为」这条声称**已经不再成立**——这是计划层面的缺陷，不是 implementer 的错
- `OrderServiceImplTest` 的申请退款用例（约 372-408 行）**仍会通过**，因为 mapper 是 mock 的——所以这个行为变化**对 CI 不可见**

**修复方向**：在 `requestRefund` 里捕获 `DuplicateKeyException`（或前置查询），返回既有退款记录或业务错误 `REFUND_ALREADY_EXISTS(50003)`。

**决定（2026-09-19）**：修。折进 **Task 3**——因为 `REFUND_ALREADY_EXISTS(50003)` 正是在那里引入的，先有错误码才能优雅返回。届时一并**修订计划第 34 行的声称**：「不改动任何现有接口的行为」在唯一索引落地后已不成立，应改为「既有接口的**正常路径**行为不变；重复提交从『静默写入第二条』变为『返回业务错误』」。

**修复方向**：把 `refund` 加进 `CLAUDE.md:367` 与 `AGENTS.md:368` 的查询，并注明「缺失会静默使退款幂等失效」。这是关闭这个洞最便宜的改动，且符合仓库既有约定（也是 K-2 的缓解措施）。

**决定（2026-09-19）**：修。作为**独立小改动**执行（只动仓库级文档，与任何任务的代码改动分开提交），在 Task 1 收尾后立即做。

## K-8 被驳回的退款会永久阻塞该订单的后续申请

| | |
|---|---|
| **状态** | **不必改代码**（2026-09-19 按「取舍准绳」判定）；**写进计划的「已知简化」清单**，见下 |
| **发现于** | 2026-09-19，Task 1 的代码质量审查（计划层问题，非实现缺陷） |
| **位置** | 计划 A 的「已知简化」清单（第 1295-1301 行）应补入 |
| **处理时机** | 商家审批流落地之前 |

**现状**：退款行**永不删除**，且没有逻辑删除列。所以一条最终为 `REJECTED` 的退款会**永久**阻塞该订单的后续退款——「先驳回、再重新申请」变得不可能。

**当前是否触发**：**否，是潜在问题**。现在没有任何代码写 `REJECTED`；`docs/implementation-plan.md:411-412` 描述的 `/api/merchant/refunds/{id}/approve|reject` 端点在代码里**不存在**（grep `module/merchant` 无退款相关代码）。

**但**：`CLAUDE.md:178` 把退款生命周期描述为 PENDING/APPROVED/REJECTED/COMPLETED，说明商家审批流是**已规划**的。届时会触发。

**需要一并决定**：Task 4 的 `refundExists` 对一条 `REJECTED` 行应当如何解释——按当前逻辑，它会让订单永久不可退。

**建议**：写进计划 A 的「已知简化」清单（那里已有三条同类条目），并明确 `refundExists` 的语义。

**关联陷阱（2026-09-19 追加核实）**：supermall 的 `application.yml` 配了 **MyBatis-Plus 全局逻辑删除**——

```yaml
mybatis-plus.global-config.db-config.logic-delete-field: deleted
logic-delete-value: 1
```

`Refund` PO 当前**没有** `deleted` 字段，所以逻辑删除不生效（这是好事，`refund` 的 `order_id` 唯一索引不会被软删除行污染）。

**但这是个陷阱**：全局配置意味着，**只要有人给 `Refund` PO 加一个名为 `deleted` 的字段**，MP 就会自动接管为逻辑删除——而**软删除的行依然占用 `order_id` 唯一索引**。届时「软删除退款 → 重新申请」看起来可行、实际仍被唯一索引挡住，且没有任何报错提示原因。

排查这一点本身就花了时间：`Refund` 的**表**和 **PO** 都没有 `deleted`，但**全局配置**存在。将来若决定用软删除解决本条，必须先处理唯一索引（例如改为 `UNIQUE KEY (order_id, deleted)` 之类的复合形式或部分索引方案），否则会得到一个静默失效的修复。

**判定（2026-09-19，按「取舍准绳」）**：**不改代码**。本条**当前不触发**——没有任何代码写 `REJECTED`，商家审批流（`/api/merchant/refunds/{id}/approve|reject`）在代码里根本不存在。现在修它等于**为一个不存在的功能做设计**。

**要做的只有一件事**：把本条写进计划 A 的「已知简化」清单（那里已有三条同类条目）。**成本是一行字，收益是显示你知道这条边界在哪**——而这恰恰是这类项目要展示的东西：不是「没想过」，而是「想过、知道边界、有意划在范围外」。

## K-10 迁移脚本的 `USE mall;` 会让临时库测试静默打到真库

| | |
|---|---|
| **状态** | **已处理**（2026-09-19，Task 1 第三轮改为 `-D mall` 并经审查独立验证） |
| **发现于** | 2026-09-19，Task 1 的修复过程中 implementer 自己踩到并上报 |

| **处理时机** | 出现第二个迁移脚本时 |

implementer 自己就是靠「把测试副本里的 `USE` 那一行替换成临时库名」才完成测试的，并主动上报了这个顾虑。

**可能的处理方向**：
- 保持现状，靠执行者自觉（脚本头部已注明「要迁移别的库只需改这一行」）
- 改为表名限定 `mall.refund`（同样需要改一处，但错改时更容易发现）
- 库名参数化（MySQL 脚本对参数化支持较差，成本高）

**决定（2026-09-19）**：**去掉 `USE mall;`，改在调用方式里写 `-D mall`。**

方案由代码质量审查者在重审时提出，它**明确承认这是它自己上轮 Minor 建议的错**——它把一个响亮的无害失败（`ERROR 1046`）换成了静默打错库的风险。新方案在四个方面更优：

| | `USE mall;`（旧） | `-D mall`（新） |
|---|---|---|
| 跨环境一致性 | 每个环境要改跟踪的文件——**正是导致 K-1 的漂移模式** | 文件逐字一致，不用改 |

| 临时库测试 | 必须改文件，忘了就打到真库 | `-D mall_scratch`，无需改文件 |
| 忘加参数 | **静默写生产库** | 无害的 `ERROR 1046` |

**注**：`information_schema` 查询用的是 `DATABASE()`，`-D` 指定的库正是它返回的值，所以判定逻辑不受影响（已要求实现时验证这一点）。

## K-12 政策枚举的两处语义边界

| | |
|---|---|
| **状态** | **不处理**（用户 2026-09-19 裁定） |
| **发现于** | 2026-09-19，Task 2 的 implementer 主动上报 |
| **位置** | `supermall/.../order/enums/AfterSalesPolicy.java` |
| **处理时机** | 不适用 |

**裁定（2026-09-19）**：**两条都不处理。** 用户理由——**本项目的目的是展现架构与技术栈，不是做生产级系统**（详见文件头的「取舍准绳」）。审查者判定这两条在生产标准下真实存在，但它们既不承载架构叙事，修了也不出彩。

因此下面审查者给出的分析**仅作为记录保留**（它们本身质量很高，将来若真要上生产可直接取用），**不作为待办**。特别地：Task 4 **不**加 `Math.max(0, …)` 守卫，`resolve` 的签名**不**改。

---

**第 1 条：负的 `daysSinceReceipt` 会被静默放行**

`SEVEN_DAY_NO_REASON.appliesTo("RECEIVED", -1)` 返回 `true`（因为 `-1 <= 7`）。

若调用方用 `now - 签收时间` 计算天数，而签收时间戳缺失、写入晚于状态变更、或存在时钟偏移，就可能得到负数并**错误命中 7 天无理由**。计划给的测试未覆盖负值。

Task 4 的 `RefundEligibilityServiceImpl` 里有个 `daysSince()` 辅助方法，它处理了 `from == null`（返回 0），但**没有处理未来的时间戳**。而 `order.created_at` 是 `NOT NULL DEFAULT CURRENT_TIMESTAMP`，所以实际触发需要时钟偏移或手工写入未来时间——**风险低**。

**决定（2026-09-19，代码质量审查判定）**：**低危。守卫放在 Task 4 的调用点，不要放在枚举里。**

两个理由：

1. **实际不可达**：Task 4 用 `Duration.between(order.getCreatedAt(), now).toDays()`，而 `toDays()` **向零截断**——现实中的主机/数据库时钟偏移（秒到小时级）得到的是 **0** 而非负数。要产生负数需要**整整 ≥24 小时**的偏移。真正可利用的窗口是「有人手工写入未来时间戳」，属于数据篡改而非运行时路径。
2. **守在枚举里会产生反效果**：加 `daysSinceReceipt >= 0 &&` 会让负数落到 `QUALITY_ISSUE` 而不是 `SEVEN_DAY_NO_REASON`——**因为一个数据故障而剥夺用户更宽松的政策**。正确做法是 Task 4 的 `daysSince` 里用 `Math.max(0, …)`，这既给出对用户有利的解读，也顺带归一化了不足一天的偏移。

**顺带发现的更大问题**：计划「已知简化 #1」（用 `order.created_at` 近似签收时间）的偏差**方向相反且更大**——订单在 `PAID`/`SHIPPED` 会滞留 1~3 天，导致**合法的第 6 天申请被拒**（过度拒绝）。若要动窗口计算，这一条比负数问题值得优先处理。

**第 2 条：7 天内的质量问题会被归类为「7 天无理由」**

这是计划**刻意锁定**的语义——`resolve_shouldReturnFirstMatchingPolicyInPriorityOrder` 明确断言「签收 2 天时返回 `SEVEN_DAY_NO_REASON`」。但 `resolve(String, long)` 的签名**看不到「用户主张的是质量问题」**，所以第 2 天提出的质量投诉会拿到「7 天无理由」的标题与条款文本。

**为什么这要紧**：两者在下游通常含义不同——**无理由退货一般运费由买家承担，质量问题一般由卖家承担**。这直接影响 Agent 组织给用户的解释，而「解释不得与判定结果矛盾」是阶段 4 的评测项之一。

**决定（2026-09-19，代码质量审查判定）**：**暂不改签名，但要加 javadoc，并绑一个具体触发点。**

**为什么现在不改**：

1. **当前不可观测**——Task 5 是整单退款，系统里**根本没有运费字段、也没有部分退款**。所以「无理由 vs 质量问题」产生**逐字节相同的用户可见结果**。唯一的真实差异（退货邮费谁承担）是系统尚未建模的字段。
2. **它不是 §4.2 的违反**——代码的判定（符合资格、依据政策 X）与政策 X 的文本是一致的；欠明确的是**输入**，不是那个配对。核心不变量完好。
3. **现在改也不便宜**——`resolve` → Task 4 → `RefundEligibilityVO.policyCode` → Task 6 端点 → 计划 B 的 MCP schema → 计划 C 的 Agent（**另一个仓库**）。这条链越长，改动越贵。

**已做（2026-09-19）**：在 `resolve` 的 javadoc 里写明它看不到申诉理由、签收 7 天内的质量投诉同样返回 `SEVEN_DAY_NO_REASON`。**这条很关键**——此前该事实**只存在于另一个仓库的 `known-issues.md`**，Task 4/6/7 的作者根本看不到。

**触发点（写进计划「已知简化」清单）**：**运费或部分退款进入模型的那一刻**。那正是两个政策产生财务差异的事件，且必然要动 Task 5/6——签名改动可以搭车，而不是变成一次跨仓库契约破坏。

**另一条候选路线**：审查者指出，由于 Task 7 按 `name()` 暴露**全部**条款，**Agent 可以自行选择引用哪条**（用户陈述缺陷时引用质量条款）——只要每一条可引用的条款都来自同一个枚举，同源性就保住了。但这条路线成立的前提是**「可引用集合 == `resolve` 能返回的集合」**，而那正是上面 I-1 那个可达性问题要保证的事。**若走这条路线，「无政策适用」路径的文案也必须来自枚举**，否则解释没有锚点（见 K-14）。

## K-13 同源在「时间维度」上会破——Task 7 的投递路径无变更检测

| | |
|---|---|
| **状态** | 待修（**在 Task 7 写计划文本时就该带上**，那时最便宜） |

## K-14 「无政策适用」这条路径的文案不是同源的

| | |
|---|---|
| **状态** | **不必修**（2026-09-19 按「取舍准绳」判定，理由见下） |
| **发现于** | 2026-09-19，Task 2 的代码质量审查 |
| **位置** | `AfterSalesPolicy.resolve` 返回 `null` 的场景；Task 4 的 `RefundEligibilityServiceImpl` |
| **处理时机** | 与 K-13 一起在 Task 7 前后决定 |

**现状**：`resolve` 对 `PAID`/`PENDING`/`CANCELLED` 返回 `null`，而 Task 4 **在本地拼出解释文案**（`"订单当前状态（X）不符合任何售后政策"`）。于是**在不合格这条路径上，面向用户的文本与判定不在同一个文件里**——正好是 §4.2 的反面。

而 spec 自己的说法是「**用户问『为什么不能退』时，给出有条款依据的解释**」——讽刺的是，「不能退」恰恰是最需要解释的场景。

计划那句文案（`"订单当前状态（X）不符合任何售后政策"`）措辞中性，**不会与判定矛盾**——它没有引用任何条款，也就谈不上「文本与判定不一致」。§4.2 管的是**政策条款文本**与判定同源，管不到「订单状态解释」这个范畴：**订单状态不是一条政策**。

硬把它塞进枚举反而要破坏 `orElse(null)` 契约和 Task 4 的 `assertNull(vo.getPolicyCode())`，**为了一致性的名义去做一件制造不一致的事**。

## K-16 「顺序即优先级」的遮蔽缺口（已修复）

| | |
|---|---|
| **状态** | **修复中**（2026-09-19 派工） |
| **发现于** | 2026-09-19，Task 2 的代码质量审查 |
| **位置** | `AfterSalesPolicy.java:36-44`（`QUALITY_ISSUE` 的 `appliesTo`）与 `:73-78`（`resolve` 的 `findFirst`） |

**问题**：`QUALITY_ISSUE` 匹配**所有** `RECEIVED` 订单，是兜底项。而 `resolve` 用 `findFirst()` 依赖声明顺序——所以**任何追加在其后的 `RECEIVED` 政策永远不可达**，而追加到末尾正是新增枚举值最自然的方式。

**审查者实测证明**（不是假设）：追加一个 `LATE_QUALITY_ISSUE`（`RECEIVED && days <= 30`），编译通过，**现有 7 个测试全部照过**。

**为什么比死代码更糟**：Task 7 会把**所有** `values()` 暴露给 Agent 侧建 RAG 索引，所以被遮蔽的常量**仍然把它的 `clauseText` 送进索引**——agent 能检索并引用一条**判定引擎永远不可能返回**的条款。代码说「不适用」，索引文本说「适用」。**这正是 §4.2 要防的矛盾，且是从正门走进来的。**

**修复**：加**可达性测试**——断言每个 `values()` 元素都能被 `resolve` 在某个输入下返回（「可达集合 == `values()` 集合」），并在类 javadoc 补警告。验证要求包含「实际追加一个被遮蔽的常量、确认新测试会红」。

**教训**：现有守卫覆盖了条款文本的**存在性**，但没覆盖常量的**可达性**。前者能靠构造函数强制，后者只能靠测试。
