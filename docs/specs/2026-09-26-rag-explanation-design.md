# 阶段 3：售后 RAG 解释层设计

> 2026-09-26。接续计划 A/B/C。本文只规定阶段 3；阶段 4 的评测集另行设计。

## 目标与已确认范围

本项目是能执行真实退款的求职作品集。阶段 3 要展示：政策解释来自与后端判定同源的目录；目录发布变化会被 Agent 消费并更新；FAQ 与商品资料可被检索，但不能决定退款资格、金额或执行动作。用户已选择原创 FAQ 与原创演示商品，商品说明只代表**当前目录**，不冒称下单时的商品描述。

完成后应能演示一次正常政策解释、一次 FAQ/商品问答、一次政策目录变更后的索引切换，以及解释层故障时退款防线照常工作。语料目标为 50–70 条有来源的文档：3 条动态政策、32 条原创 FAQ、至少 15 条原创且当前上架的演示商品说明；不拆分三条政策凑数。

## 已有契约与边界

- supermall 的 `GET /api/after-sales/policies` 返回 `Result<PolicyCatalogVO>`；MCP 的 `list_policy_clauses` 解开 Result 后给出单层 `{fingerprint, clauses}`。`PolicyCatalogVO` 从不可变的同次条款快照计算小写 SHA-256 指纹，覆盖 `code`、`title`、`clauseText` 和枚举顺序。指纹**不证明**执行规则与文本语义相符。
- `get_refund_eligibility` 给出 `eligible`、`reason`、`policyCode`、金额及已有退款记录，但目前没有目录指纹。阶段 3 为该响应增量加入 `catalogFingerprint`。supermall 的政策目录端点与资格服务须调用**同一个**目录构造入口取得不可变快照及指纹，不复制哈希算法。解释器只有在资格指纹与所用索引代次指纹相同时，才可引用某条政策。不可退时只依据后端 `reason` 说明当前订单结论，不自行挑政策。
- Agent 仍只用用户 JWT 经独立 MCP 进程访问 supermall，不直连数据库。政策目录和商品资料都是只读工具。退款仍只能由本地 `request_refund` 经可信事实重读、独立复核后调用 `submit_refund`；RAG 组件没有这两个写工具，也不持有商家或后端密钥。
- `QUALITY_ISSUE` 只是现有兼容码。解释不得声称质量证据已核验、退货物流存在，或把商品当前描述当作下单时的承诺。

## 方案选择

采用**后置解释层**。现有决策 Agent 完成查证、动作选择与复核/执行后，可通过一个只记录请求、不返回任何语料的本地工具提出解释需求；可信编排层再查询需要的事实与资料。解释生成器是一次无工具的模型调用，不是第三个拥有决策职责的 Agent。退款金额、状态和人工升级结论由可信代码输出；解释文本既不能覆盖也不能作为这些结论的依据。

直接把检索工具交给决策 Agent 虽然改动少，但无法结构性证明检索语料没有影响 `request_refund`。另建解释进程可进一步隔离，却增加接口和部署复杂度；本阶段保持解释服务在 Agent 进程内。保留决策 Agent 与复核 Agent 两个角色。

### 一轮请求的数据流

1. 决策 Agent 仍见订单、物流、资格等现有只读 MCP 工具及本地退款/升级动作，但不再直接看 `list_policy_clauses` 或 RAG 索引。新增本地 `request_explanation(orderId)` 只记录本轮候选订单 ID（无订单时为 0），向模型返回固定确认语，不返回检索内容。它没有执行能力。决策提示词要求政策、FAQ、商品问题调用此工具；普通查单/物流查询继续沿用现有答复路径，避免重构不相关的只读事实采集。
2. 每轮开始时清空解释请求。`agent.handle` 返回后，可信编排层先取 `RefundRequestTools` 的本轮确定回执；若有回执，只输出回执，不附模型解释。否则检查本轮新增的 `EscalationTools` 记录；若有升级，只按记录生成“已记录并请联系人工客服”的回复。两类动作优先于解释请求，因此模型无论调用顺序如何，都不能用解释内容改写执行结果。同会话历史升级记录不得被当作本轮动作。
3. 仅当本轮没有退款或升级动作且确有解释请求时，可信代码处理解释。若请求涉及多个不同订单，或与用户输入中明确写出的订单 ID 不同，要求用户明确目标；若只有一个一致的订单 ID，后置代码以同一用户 JWT 经 MCP **重新调用** `get_refund_eligibility`，检查工具成功、JSON 结构、返回 `orderId` 与请求一致以及 `eligible/refundExists` 等必需字段。模型传入的 ID 只是查证目标，不是可信资格事实；绝不从模型答复或 trace 反推订单。没有订单 ID 时只能给一般政策/FAQ/当前商品说明，不得声称某笔订单符合条件。
4. 对订单政策解释，消费者刷新政策目录，再核对资格的 `catalogFingerprint`、`policyCode` 与目录条款。匹配才按 code 精确取条款，不做“相似条款替代”；订单资格结论使用可信模板，政策正文用原文引用。不可退、已有退款、响应缺字段或指纹不匹配时，不引用目录条款；可退但目录不可用时明确说暂无法引用政策正文。**没有订单 ID 的一般政策问题**可列示本次刷新目录中的至多三条原文，并明确“这是一般规则，不代表某笔订单的资格”；不得按相似度挑一条并当作订单结论。
5. 对 FAQ 或当前商品问题，检索器根据**原始用户输入**返回带来源 ID 的片段；商品引用前重新确认详情仍上架。无工具的生成器只能拟写非交易补充说明并给出来源 ID，不能生成订单资格、金额或执行状态。来源 ID 不在候选集、格式不合格、出现当前订单退款/到账等交易结论，或生成失败时，整段生成文本丢弃，改用代码引用来源原文或说明无可靠依据。
6. 没有解释请求的普通查单/物流轮保持现有模型答复；这一既有路径不冒称为 RAG 解释。解释层故障不得触发退款重试、改变既有回执或改写订单状态。

## 索引与更新

政策消费者每次准备引用政策前调用一次 `list_policy_clauses`。它校验 MCP `isError`、非空文本、单层 JSON 对象、非空指纹、唯一 code、非空标题与条款文本；从**这同一次响应**构造候选不可变索引。刷新过程串行化，指纹变化时先完整构建，再原子切换 `{fingerprint, documents, retrievalIndex}`，避免旧请求晚完成而覆盖新代次；一轮检索固定使用一个代次。顺序变化也应触发切换。消费者不能把“模型调用过目录工具”当成刷新证据。

索引采用进程内、可重建的轻量词项检索：订单相关政策按 `policyCode` 精确匹配，一般政策问答列出完整目录；FAQ/商品按中文相邻字词与英文/数字词项建立确定性排名，并记录命中的来源 ID。政策代次由目录指纹标识；静态 FAQ 有仓库内容摘要；每个商品问答轮重新扫描分页的当前上架商品列表，只保留演示清单内的商品，以当前内容摘要刷新商品子索引，候选详情再复查上架状态。商品变化不冒充政策指纹变化。50–70 条演示语料不需要外部向量数据库或额外 embedding 凭据。后续阶段 4 可用同一语料比较词项与向量检索，但不把选型推迟到运行时。

目录拉取、校验或新索引构建失败时，当前请求不引用旧政策文本；原有索引可保留以便下次成功刷新时比较，但标为不可引用。若 `catalogFingerprint` 与资格响应不一致，也不引用条款。退款通路不依赖目录可用性。只记录无凭据的指纹、代次、引用 code 和降级原因；不把订单号或模型输入塞进现有 `TASK6_TRACE`。K-13 只有在消费者刷新、切换、失败降级和真实接线均通过后才可标“已处理”；K-48 留给阶段 4 评测归因设计。

## 语料来源与商品边界

- **政策**：只取 supermall 目录三条，带 `code`、`fingerprint`、标题、正文和源类型。FAQ 不能新增或改写退款窗口、金额、质量核验等交易规则。
- **FAQ**：仓库内维护 32 条原创、可审阅的非交易规则文档，逐条保存稳定 ID、标题、正文、事实依据（代码或已验收契约）和复核日期。内容涵盖查单、退款状态解释、异常时联系人工、未支持能力等；文字与当前实现逐条核对。
- **商品**：准备 15–35 个原创演示商品，经商家业务 API 在测试环境创建/上架；种子数据使用稳定逻辑 ID，实际商品 ID 写入该环境被 Git 忽略的清单。运行时通过新增的只读 MCP 商品列表/详情工具获取这些演示商品的当前名称、描述与 SKU 规格；不索引清单外的商家内容，也不收录下架商品。列表逐页拉取，候选商品引用前复查详情与上架状态；拉取失败时不引用缓存的商品描述。演示数据和脚本可入库，JWT/密钥不入库。商品评价、图片、用户订单原因及用户标识不进语料。
- **历史描述**：当前订单没有可验证的下单时商品描述快照或可靠的订单到商品详情关联。对“收到的商品与当时描述是否一致”只能说明无法据当前目录核定历史承诺，并指向人工核查；阶段 3 不作真伪裁决。

## 安全与故障语义

所有检索文本均视为数据，包括商家商品描述；其中的命令、角色扮演或“直接退款”话术不能进入决策/复核上下文。解释生成器没有工具，其输出也不能成为 `request_refund` 的输入。订单资格、金额、退款状态和人工升级由可信模板独占；模型生成段只用于 FAQ/商品的非交易补充。代码校验其来源 ID，并拒绝当前订单退款、到账、资格、金额或执行结论；拒绝时丢弃**整个**生成段。政策正文使用目录原文而非模型改写。无可靠来源时不编造条款或商品事实。政策与商品可用性分别降级，不牵连退款或人工升级。自然语言语义无法仅靠格式检查完全证明；残余误述由本阶段针对性测试和阶段 4 系统评测检查。

资格查询和目录拉取是两个 HTTP 请求。增加 `catalogFingerprint` 后，解释器可检测跨部署版本错配并拒绝引用；它不消除两次请求的时间间隔，但保证**被引用的代次**与资格响应一致。条款文字与规则实现的语义一致性仍由 supermall 现有枚举/资格/执行测试和代码审查守护，不由哈希保证。

## 验收与证据

1. 单元/协议测试覆盖目录解析、指纹和条款变化、枚举顺序变化、候选构建失败时不引用旧条款、资格指纹不匹配、资格返回的订单 ID/字段无效、未知/重复 policyCode、FAQ/商品来源 ID 校验及上架状态变化。
2. 架构测试证明决策模型可见工具中没有政策目录、RAG 索引或 `submit_refund`；`request_explanation` 不返回语料，解释生成器没有任何动作工具；复核仍独立重读事实，同会话驳回仍终止该订单。原有查单/物流轮无解释请求时仍能答复。
3. 解释测试覆盖退款/升级动作优先于同轮解释请求、历史升级不串轮、不可退只用后端原因、`QUALITY_ISSUE` 不冒称质量核验、已有退款与执行不确定不说已退款、多订单不串引用、恶意 FAQ/商品文本无法触发动作；生成文本冒称订单已退款或到账时整段丢弃。
4. 在测试环境通过 MCP 与真实 supermall 验证旧/新目录指纹及条款正文同步切换、失败降级，以及接入解释层前后相同订单的退款/复核结果不变。测试订单和演示商品只经正常业务 API 创建；数据库只读核对，不由 Agent 直写。
5. 记录语料清单、来源及样本解释；标明当前商品说明和下单历史说明的边界。阶段 4 再定义 240 条系统化评测集、解释一致性指标和跨模型比较，不能拿本阶段少量用例冒称完成阶段 4。

## 不在阶段 3 内

不做订单商品历史快照、评价索引、外部向量库、自动改写政策、RAG 判定资格或金额、增加第三个决策 Agent、生产级索引服务与阶段 4 全量评测。JDK 17 运行验证和 K-48 的持久 trace 归因仍按原记录另行处理。
